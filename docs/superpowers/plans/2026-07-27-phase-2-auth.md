# Phase 2 — Auth end to end

**Goal:** A real person can sign up, log in, stay logged in across reloads, and log out — and `/(app)` routes stop being publicly readable.

**Architecture:** Supabase Auth owns credentials and sessions. The browser holds the session in cookies via `@supabase/ssr`. `proxy.ts` performs an optimistic guard and refreshes the session on every request. Pages stay server components; `services.ts` swaps its mock return for `serverFetch`, which forwards the session's access token to FastAPI as a bearer. The real authorization boundary remains the API's JWKS verification (Phase 1) — the proxy guard is UX, not security.

**Prerequisite met:** Phase 1 shipped ES256/JWKS verification, so a token minted by Supabase now actually verifies at the API.

---

## Next.js 16 facts this plan depends on

Verified against `frontend/node_modules/next/dist/docs`, not from memory. `frontend/AGENTS.md` exists precisely because this version diverges.

| Fact | Consequence |
|---|---|
| **`middleware.ts` is renamed `proxy.ts`** (Next 16). Named export is `proxy`. | A file called `middleware.ts` is silently ignored. The guard would never run and every "protected" page would stay public. |
| `proxy` runs on the **Node.js runtime**; edge is unsupported and not configurable. | `@supabase/ssr` works there without edge-compat concerns. |
| `cookies()` is **async** — `await cookies()`. | Every server-side Supabase client must be constructed in an async function. |
| Proxy is documented as **not** a session-management or authorization solution — "optimistic checks" only. | Authorization stays in FastAPI. The guard only prevents a logged-out user seeing an app shell. |
| Turbopack is the default bundler. | No custom webpack config. |

## @supabase/ssr 0.12.3 facts

| Fact | Consequence |
|---|---|
| `setAll(cookiesToSet, headers)` takes a **second `headers` argument** carrying `Cache-Control: private, no-cache, no-store...`. | Dropping it lets a CDN cache a response containing another user's session cookie. On Vercel that is a live cross-user session-leak risk. It must be applied to the response. |
| `getClaims()` is preferred over `getSession()` for projects on asymmetric signing keys. | Ours is ES256. `getClaims()` verifies locally against JWKS — no per-request network call, and unlike `getSession()` the result is trustworthy. |
| `getSession()` on the server returns cookie data that "must not be trusted". | Never gate on it. |

## Global Constraints

Inherited from [the roadmap](2026-07-27-ship-roadmap.md#global-constraints), plus:

- **Pages never call `apiFetch`/`serverFetch` directly.** All data access goes through `src/lib/services.ts`.
- **`NEXT_PUBLIC_*` is the only prefix the browser may see.** No secret reaches a client component.
- The route guard is optimistic. **Never** treat proxy as the authorization boundary.
- No `dangerouslySetInnerHTML` anywhere. The codebase has zero today; it stays zero.
- Conventional Commits. No `Co-Authored-By` or AI attribution.

### Task 1: Server-side Supabase clients and the route guard

**Files**
- Create `frontend/src/lib/supabase/server.ts` — `createClient()` using `await cookies()`
- Create `frontend/src/lib/supabase/proxy.ts` — `updateSession(request)` returning `{ response, claims }`
- Create `frontend/src/proxy.ts` — named `proxy` export + `config.matcher`
- Modify `frontend/src/lib/supabase/client.ts` — comment clarifying browser-only use

**Behaviour**
- Unauthenticated request to any `/(app)` route → 307 to `/login?next=<pathname>`
- Authenticated request to `/login` or `/signup` → 307 to `/dashboard`
- Session cookies refreshed on every matched request, with the `headers` from `setAll` applied to the response
- `matcher` excludes `_next/static`, `_next/image`, `favicon.ico`, and static assets, so the guard does not run on every image

**Acceptance:** logged-out `/dashboard` redirects to `/login?next=/dashboard`; the landing page `/` stays public; a response that sets auth cookies carries `Cache-Control: private, no-cache, no-store, must-revalidate, max-age=0`.

### Task 2: Auth server actions and wired forms

**Files**
- Add `zod` as a direct dependency (present only transitively today)
- Create `frontend/src/lib/validation/auth.ts` — `signInSchema`, `signUpSchema`
- Create `frontend/src/app/(auth)/actions.ts` — `signIn`, `signUp`, `signOut` server actions
- Create `frontend/src/components/auth/auth-form.tsx` — shared client form using `useActionState`
- Modify `frontend/src/app/(auth)/login/page.tsx` and `signup/page.tsx` — render the client form
- Create `frontend/src/app/auth/callback/route.ts` — OAuth/email-confirmation code exchange

**Behaviour**
- Validation runs on both sides. Server-side validation is the one that counts.
- Errors render inline under the offending field (this is FE-07 from the ship-gate audit).
- `signIn` success → `redirect(next ?? "/dashboard")`.
- `signUp` → if the project requires email confirmation, show "check your email" rather than pretending the user is logged in.
- The error message for a wrong password and an unknown email must be **identical** — distinguishing them is a user-enumeration oracle.
- "Continue with Google" is removed unless the provider is actually configured. A button that does nothing is worse than no button.

**Acceptance:** signup creates a Supabase user; login sets session cookies and lands on `/dashboard`; wrong password shows an inline error and no stack trace; logout clears cookies and a back-button press does not restore the app shell.

### Task 3: Server-side API fetch, and the first real data

**Files**
- Create `frontend/src/lib/api/server.ts` — `serverFetch<T>(path, init)`
- Modify `frontend/src/lib/api/client.ts` — switch `getSession()` to `getClaims()`-safe usage; keep for client components
- Modify `frontend/src/lib/services.ts` — `getProfile()` calls the real API; the rest stay mock with a comment naming their phase
- Modify `frontend/src/types/index.ts` — `Profile` matches the API's `ProfileOut`
- Modify `frontend/src/app/(app)/layout.tsx` / `topbar.tsx` as needed for the new shape

**Behaviour**
- `serverFetch` reads the access token from the server-side Supabase client and sends `Authorization: Bearer <token>`.
- A 401 from the API → redirect to `/login` (the session died server-side).
- Errors surface as `ApiError` with status; no response body is interpolated into UI without escaping.

**Acceptance:** a logged-in user's real name/level/XP render in the topbar, sourced from Postgres — the first end-to-end path from browser to FastAPI to Supabase. `GET /profile` auto-creates the row on first visit, closing the one Phase 1 exit criterion that needed a real user.

### Task 4: Error boundaries, 404, and logout affordance

**Files**
- Create `frontend/src/app/error.tsx`, `global-error.tsx`, `not-found.tsx`
- Modify `frontend/src/components/layout/topbar.tsx` — account menu with Log out
- Modify `frontend/next.config.ts` — security headers for the frontend

**Behaviour**
- A thrown render error shows a branded recovery screen with a `reset()` action, never a white page or a stack trace.
- Security headers: CSP, `X-Content-Type-Options`, `Referrer-Policy`, `X-Frame-Options`, and HSTS in production.

**Acceptance:** a deliberately thrown error renders `error.tsx`; an unknown URL renders `not-found.tsx`; `curl -I` on the dev server shows the security headers.

## Phase 2 exit criteria

- [ ] `npm run build` green; `npm run lint` clean; `npx tsc --noEmit` clean
- [ ] Logged-out `/dashboard` → `/login?next=/dashboard`; `/` stays public
- [ ] Signup → login → `/dashboard` → logout → `/dashboard` redirects again
- [ ] Topbar shows real profile data from Postgres
- [ ] `career_profiles` gains exactly one row per signed-up user
- [ ] Wrong password and unknown email produce byte-identical error text
- [ ] No secret in any client bundle: `grep -r "sb_secret\|service_role" .next/` returns nothing
- [ ] `/(app)` routes are no longer statically prerendered
